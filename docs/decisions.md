Risk: a Vercel build command that skips `prebuild` would break the `api/` functions. Spec: [CHG-0024](specs/changes/0024-chat-knowledge-base-pipeline.md).
- The user chose to write **catch-up specs** for work that shipped without one: CHG-0024 (chat knowledge base) and [CHG-0025](specs/changes/0025-public-assets-and-seo-files.md) (public assets, icons, SEO files). ## 2026-11-18 - Implementation Phase 4 complete: CORS lockdown + rate limiting

**What changed:**
- Added `api/_lib/request-guard.ts`, a shared helper module (excluded from Vercel's
  automatic route generation by its underscore-prefixed folder) exporting
  `buildCorsHeaders()` and `checkRateLimit()`.
- `buildCorsHeaders()` replaces the wildcard `Access-Control-Allow-Origin: '*'`
  previously hardcoded in both `api/chat.ts` and `api/contact.ts` with
  `https://${process.env.VERCEL_PROJECT_PRODUCTION_URL}`, falling back to `'*'`
  only when that env var is absent (i.e. local dev). Per the user's decision
  ("Vercel default domain"), this avoids hardcoding a guessed `*.vercel.app`
  project slug - Vercel sets this var automatically on every deployment to the
  project's real production domain.
- `checkRateLimit()` enforces 10 requests/minute per client IP using Upstash
  Redis + `@upstash/ratelimit`'s sliding-window limiter, per the user's decision
  ("Upstash Redis") and the backend-patterns skill's guidance to never use an
  in-memory per-process counter in a serverless function (it resets on every
  cold start and isn't shared across instances). If `UPSTASH_REDIS_REST_URL`/
  `UPSTASH_REDIS_REST_TOKEN` aren't set, it fails open (skips rate limiting,
  logs a warning) rather than breaking the endpoints outright.
- Both `api/chat.ts` and `api/contact.ts` now import and call these helpers
  instead of defining their own local `corsHeaders` const, and both return
  early with the 429 response when rate-limited.
- Added `@upstash/ratelimit` and `@upstash/redis` to `package.json`.
- Added blank `UPSTASH_REDIS_REST_URL=` / `UPSTASH_REDIS_REST_TOKEN=`
  placeholders to `.env` with a comment on where to get real values.

**Action needed from the user before this works in production:**
1. Run `npm install` locally - this session's container can't reach the npm
   registry, so the two new dependencies are declared in `package.json` but
   not yet installed into `node_modules`.
2. Create a free Redis database at https://console.upstash.com/ and fill in
   `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN` in `.env` (and in
   Vercel's own project environment variables for the deployed site).

**Why not a different rate-limit store:** A Vercel KV store or a database
table would also work, but Upstash's REST-based Redis client is what the
backend-patterns skill's examples use for exactly this edge+Node dual-runtime
case, and it needs no persistent TCP connection (works from both the edge
runtime used by `api/chat.ts` and the Node runtime used by `api/contact.ts`).
